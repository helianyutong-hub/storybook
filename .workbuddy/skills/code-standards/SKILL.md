> ⚠️ 适用边界（最高优先级，必须首先遵守）
> 本规范只作用于「新增代码」与「本次任务明确要修改的代码」。
> **严禁**为了符合本规范而对存量可用代码做目录迁移、文件重命名、批量重构或拆分重写——
> 这类改动极易破坏线上已有功能，违背本文件核心约束「一定不能影响到已有功能」。
> - 存量文件保持原样；只有本次任务正好改到它、且改动安全时，才顺手对齐规范。
> - 本项目现有目录已为 `src/pages`、`src/components`、`src/lib`、`src/types`（与规范精神一致），新代码优先沿用现有目录约定，不要引入 `app/` 与现有结构并行的冲突布局。
> - 文件/函数行数限制是「新代码」红线；存量超长文件**不要**为了达标而拆分重写。

# 代码规范
## 目录结构
- 前端页面放 app/ 目录
- 后端接口放 app/api/ 目录
- 公共组件放 components/ 目录
- 工具函数放 lib/ 目录
- 类型定义放 types/ 目录

> 💡 本项目现有目录（改动时优先沿用，不要新建冲突布局）：
> 前端 `src/pages`（页面）、`src/components`（含 `ui/` 公共组件）、`src/lib`（工具）、`src/types`（类型）；
> 后端 `src/modules`（接口/模块）、`src/lib`、`src/types`。
> 新代码放在对应现有目录下即可，无需改成 `app/`。

## 文件与函数
- 每个文件不超过 400 行（超过就拆）
- 每个函数不超过 50 行（超过就拆）
## 命名
- 变量名用完整英文单词，不用 data/tmp/helper/result
- 函数名用动词开头：getUserById、createOrder、sendEmail
- 布尔变量用 is/has/should 开头：isActive、hasPermission、shouldRetry
- 不用 handle/process/do 这种空动词
## 类型
- 所有 API 接口的请求和返回类型定义在 types/api.ts
- 禁止用 any，用 unknown 代替
## 注释
- 注释写"为什么这么做"，不写"做了什么"
- 代码本身应该说明做了什么
## 错误处理
- 不要 try-catch 静默吞错误
- 出错就抛具体异常或返回明确错误信息
