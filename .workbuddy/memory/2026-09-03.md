## 第四轮修复：Player 页 needsTap 与「语音准备中」冲突（本 session，已上线）
- **用户反馈**：微信播放页同时显示「轻触屏幕任意位置，开始播放」和「· 语音准备中」，但点了屏幕没反应（音频还没准备好）。两个提示互斥不该同现。
- **根因**：`needsTap`（轻触提示）与 `audioMode === 'none'`（语音准备中）是独立条件，无互斥。音频未就绪时 `needsTap` 被置 true（play() 被自动播放策略 reject），但此时 `currentAudioUrl` 为空、`resumeByTap` 空操作 → 点了没用。
- **修复（Player.tsx）**：
  1. 中间「轻触屏幕」提示条件加 `audioMode !== 'none'`（只在音频真正就绪但被拦截时才显示）
  2. 吸底「点击这里开始播放」按钮同样加 `audioMode !== 'none'`
  3. 新增等待提示：当 `playing && audioMode === 'none' && !audioGen && !audioError && !needsTap` 时显示转圈「语音准备中…正在加载语音」
  4. 三种状态现在互斥：生成中 / 轻触提示(音频就绪) / 语音准备中(未就绪) / 出错
- **改动文件**：`frontend/src/pages/Player.tsx`（3 处条件 + 1 处新增等待面板）

## 第六轮修复：语音加载 405 错误 + 无法试听（本 session，已上线）

## 第七轮优化：语音加载速度大幅提升（本 session，已部署）
- **用户反馈**：预览页试听和播放页语音都加载特别慢，没法等没法使用（截图显示"语音服务正在启动中"卡住）
- **根因**：每次都要等 Render 冷启动 + 实时生成所有页音频，无缓存无预加载
- **4 项优化**：
  1. **localStorage 音频缓存**（api.ts）：生成的 audioUrls 按 storyId 存入 localStorage（24h TTL），第二次打开同一故事秒开；新增 `getCachedAudioUrls`/`setCachedAudioUrls`/`invalidateAudioCache`
  2. **Preview 页后台预生成**（Preview.tsx）：进入预览页后立即调用 `ensureStoryAudioUrls` 后台静默生成所有页音频（用户看文案时就在生成）；同时发一个轻量 POST /tts 请求唤醒 Render 后端（减少冷启动等待）
  3. **Player 页边播边生成**（Player.tsx）：不再等全部页生成完才播放 → 先从 localStorage 缓存读取（秒开）→ 有音频的页立即播 → 没有音频的当前页等 2 秒重试（后台可能刚生成完）→ 仍没有则跳到下一页；后台继续生成剩余页
  4. **重新生成文案时清除缓存**（Preview.tsx `regenerate`）：调用 `invalidateAudioCache` 避免旧音频残留
- **改动文件**：`frontend/src/lib/api.ts`（缓存层+ensureStoryAudioUrls重写）、`frontend/src/pages/Preview.tsx`（预生成+预热+清缓存）、`frontend/src/pages/Player.tsx`（缓存优先+边播边生成）

### 关于「是否需要换后端」的分析
- **Render 免费层两大硬伤**：① 15 分钟无访问自动休眠（冷启动 30-60 秒）② CPU/内存受限（TTS 合成 10 页需 30-60 秒）
- **前端优化能做到的上限**：缓存（解决重复访问）+ 预生成（转移等待时间）+ 边播边生成（不等全部完成），但**首次访问 + 后端休眠后**必然慢
- **如果要真正解决速度问题**：
  1. **Render 付费 $7/月**：不休眠 + 更多资源，彻底解决冷启动
  2. **Railway $5/月**：同上，略便宜
  3. **免费保活**：UptimeRobot（免费）每 14 分钟 ping 一次 Render，防止休眠（只解决冷启动，不解决 TTS 速度）
  4. **国内服务器**：最快但需备案+付费
